# BuildWatch account-system activation

The account features are integrated into the existing Expo app and Node API. Public maps remain usable with no account. No external account was created, no live subscription was charged, and no initial administrator was assigned during implementation. You can ask Codex to perform the commands and configuration work below; you do not need to open Terminal. You must own and complete provider sign-ins, agreements, billing, and store credentials yourself.

## Current architecture and what was preserved

The original map, project editor, meeting screens, status/search filters, and five demo projects are retained. The previous shared-key/local-write bypass is retired: map changes now require authenticated collaborator/admin permissions. Existing `server/data/projects.json` is imported once into `projects.json.sqlite` and retained as a backup; new saves use SQLite transactions and revision checks. Account profiles, roles, follows/history, invitations, corrections/feedback, entitlements, notifications/devices, and project edit history live in that same server database. SQLite is accessed only by the server; there is no client SQL access or client role flag. Supabase was not present, so no duplicate Supabase tables or second password store were introduced. Auth0 handles passwords and identities. No forum implementation exists in this checkout; none was removed or rebuilt.

The migration fails rather than resetting data if the existing file cannot be imported. The migration marker stops reseeding on future boots. Keep the persistent data directory private. For a running WAL database, use SQLite's backup mechanism or VACUUM INTO for consistent backups rather than copying the main database alone. Restore backups before restarting after a failed migration. Do not run old shared-key releases against the same published service.

## 1. Configure sign-in and activate your personal administrator account

Create an Auth0 tenant. In that tenant create:

- A **Single Page Application** for the website.
- A **Native Application** for iOS, with Authorization Code + PKCE and rotating refresh tokens. Enable offline access for the API.
- An API with a unique audience (for example `https://api.your-buildwatch-domain.com`) and RS256 signing.
- A Machine-to-Machine application authorized for the Auth0 Management API, with the minimum necessary `read:users`, `update:users`, `delete:users` permissions for linking, initial admin MFA metadata, and account deletion. Verify your tenant's exact linking scope requirements; keep these credentials on the server only.

Set the website origin as an allowed callback, logout URL and web origin. For local preview that is `http://127.0.0.1:8765`. Set `buildwatch://auth` as the native callback/logout URL. Use an HTTPS origin in production. Browser auth uses memory caching and silent session renewal; configure an Auth0 custom domain/same-site deployment if browser third-party-cookie restrictions prevent silent login after reload.

Copy `.env.example` to `.env` for public client IDs/domain/audience. Copy `.env.server.example` to `.env.server` for the server configuration. The server and bootstrap CLI load `.env.server` at startup; Expo loads `.env` for compilation. Hosting should inject secrets via encrypted environment settings. Ask Codex to help set these values without pasting secrets into this chat. Set `AUTH0_ISSUER` to the full HTTPS tenant issuer (including its trailing slash), and use the same audience on both sides. Management API credentials must never have an EXPO_PUBLIC prefix. Set AUTH0_PASSWORD_CLIENT_ID to the SPA application's ID to enable reset emails from Settings.

Deploy two Auth0 **Post Login Actions** in order: first `server/accounts/auth0-mfa-action.js`, then `server/accounts/auth0-action.js`. Attach both to the Login flow in that exact order. The first Action uses pipeline-pausing OTP enrollment/challenge APIs; the second reads the completed MFA method and emits claims. Do not replace this with api.multifactor.enable in the claims Action, because that legacy challenge runs after the Actions and omits the current MFA proof. Use New Universal Login and enable the OTP authenticator factor. It adds the signed email, verification, connected-method and authentication claims consumed by the backend. Enable email verification and configure production email delivery/SMTP in Auth0. Configure authenticator/TOTP MFA. Tenant plans can differ in MFA and linking availability. Do not remove the backend MFA requirement to work around configuration failures.

Sign in to BuildWatch with **your own account** and verify its email. Ask Codex to identify that existing account's Auth0 subject in the local users table and run the one-time bootstrap against it using `pnpm admin:bootstrap '<your Auth0 subject>'`. This is an operator-only command, not a public HTTP endpoint. It assigns the sole initial admin, marks the one-time setup consumed, records the role change, and sets Auth0 metadata that requires MFA. There is no hardcoded password or shared admin code.

Log out and sign back in. Complete MFA enrollment/challenge. The Admin Dashboard will reject requests until a signed authentication-method claim confirms MFA. Test denial without MFA and success after MFA in your actual tenant. Only this bootstrap procedure creates an admin; the UI can promote/demote collaborators, not create additional admins. The sole admin cannot be disabled or deleted through the app. Any future ownership transfer is an operator-reviewed database/provider operation.

## Secure map administration

After signing in as the configured administrator and completing MFA, open **Menu → Edit Map** or **Admin Dashboard → Edit Map**. Search all developments, open an existing development to change its information or pin, or choose **+ Add development**. Publish writes to the shared database with revision conflict checks and a record of who changed it and when. The History button shows saved project revisions. **Project Management** separately lists projects you personally edited.

Guest and ordinary paid/free accounts cannot open the editing API. An admin session without MFA must choose **Complete administrator verification** before editing. Collaborators need a verified account and an active server-assigned role. Revocation is rechecked immediately before a project is committed, including after the request body arrives. There is no shared editor password or localhost bypass.

## 2. Invite your first collaborator

Open **Menu → Invite Collaborators**, enter their email and create an invitation. Share its generated link privately. Tokens are random, stored as hashes, single-use, and expire after seven days by default (`INVITATION_DAYS`, maximum 30). PUBLIC_APP_URL must point to the browser app before invitations can be created.

The recipient opens the link, signs in with that exact verified email, and accepts the token in Settings. The browser retains it while redirecting through sign-in. An iPhone user can paste the token from the link into Settings until associated-domain universal links are configured. There is no public collaborator registration page. Administrators can revoke access immediately via **Manage Users**; subsequent edit requests are denied even with an existing sign-in token. Collaborators receive Plus tracking without paying. Admin project/role history records changes.

## 3. Google, Apple and email signup

Enable Auth0's `google-oauth2`, `apple`, and database/email connections for both applications. Put your own production Google OAuth and Apple service/client credentials into Auth0; avoid Auth0 development keys in production. Configure Google's authorized origins/redirect to Auth0 and Apple's service ID, team/key details, return URL, and required domain verification. Apple keys/secrets can expire and require rotation.

Users choose Continue with Google, Continue with Apple, or Continue with Email. Both web and native use the system browser/provider Universal Login; passwords, email verification, registration and Forgot Password are handled by Auth0. iOS uses a custom-scheme development/release build and PKCE; this full auth/purchasing flow is not an Expo Go/Snack feature. Guest browsing does not launch a login prompt until the user requests a registered-only action. A guest's selected development is remembered across sign-in.

Auth0 subjects, not email matches, identify accounts. Do not enable automatic email-based account-linking Actions/extensions. Settings links a new identity only after recent authentication of both accounts; the server verifies both access tokens and invokes the Management API. Existing free accounts can be explicitly linked after proof of both identities: follows, follow history, notifications, suggestions and device registrations are moved to the primary account, with the stricter notification preferences retained. The primary profile and role remain authoritative, and extra saved follows remain paused under the free allowance. Accounts with billing history or elevated secondary permissions require an operator-reviewed transfer, so billing and privileges are never silently discarded or promoted. Do not manually merge users by matching email. Test Google → logout → same Google login, Apple private-relay email, email verification/recovery, native refresh rotation, and cross-device access before release.

## 4. Configure and test $9.99/month BuildWatch Plus

Use one RevenueCat project for iOS and web. Create the `buildwatch_plus` entitlement, a monthly product (recommended ID `buildwatch_plus_monthly`), and a current offering with a monthly package. In App Store Connect create an auto-renewable subscription priced at **US $9.99/month**, configure its subscription group, review metadata, agreements/tax/banking and store signing. RevenueCat's native SDK makes the iOS StoreKit purchase; no web checkout is offered in the iOS purchase path.

For web, configure RevenueCat Web Billing with a supported billing provider such as Stripe, create its $9.99/month product and link it to the same entitlement/offering. Add the public iOS/web SDK keys to their EXPO_PUBLIC variables and the RevenueCat secret API key only to `.env.server`/host secrets. Customer App User ID is the stable BuildWatch database UUID returned by the authenticated API, shared across devices. Configure RevenueCat restore/transfer behavior to **keep purchases with the original account**; do not allow a restore to transfer someone else's subscription by switching app IDs.

Configure the authenticated HTTPS webhook `/api/webhooks/revenuecat` with `Authorization: Bearer <REVENUECAT_WEBHOOK_SECRET>`. The handler never accepts entitlement fields from the app or trusts event order: it fetches current subscriber state with the server key, updates expiry/store/management link, and deduplicates event IDs. Purchase/restore also asks the server to reconcile. Expiry (including provider-verified billing grace periods) is enforced from timestamps on every entitlement check. Plus cannot grant a role. Cancelled subscriptions keep benefits through their verified expiry. All follows and follow history are retained afterward, with one active development that the user can select.

Keep `BILLING_ENABLED=false` until sandbox end-to-end tests pass. Use a separate test environment with `BILLING_ALLOW_SANDBOX=true`, StoreKit sandbox testers/TestFlight, and the web provider's test mode. Test purchase, renewal, cancellation, billing failure, expiry, restore, cross-device login and the management portal. Verify late/duplicate webhook behavior and that modifying a client plan value never grants access. Then disable sandbox acceptance in production, set BILLING_ENABLED=true, and rebuild/redeploy the clients. The UI shows localized checkout terms; verify the US base price and localized prices in each store. No live purchase has been tested in this checkout.

## 5. Configure notifications

The in-app Notifications inbox is connected to real project publications and approved corrections. Master/update/meeting/reminder preferences are stored on the account. Only actively followed developments generate notifications. A server timer checks meetings every minute and generates a deduplicated reminder within the next 24 hours. Preferences and current entitlement/follow state are checked again before push dispatch, so expired/paused tracking does not continue sending new pushes.

Device push is **not activated by default**. Link this app to an EAS project, add its real projectId in Expo `extra.eas.projectId`, configure APNs credentials in Expo/EAS, enable Expo push-service access-token security, and store the Expo access token on the server. Use an installed signed iPhone build, not Expo Go. Run the server continuously so the scheduler/outbox runs; horizontal multi-worker delivery requires a shared database and leasing before scaling.

After setting `PUSH_DELIVERY_ENABLED=true` in a test environment, click **Enable notifications on this iPhone** in Settings/Notifications. Only this user action requests OS permission and registers the Expo token. Test accepted and denied permissions, preference changes, status updates, meeting changes, reminders, paused free-tier follows, logout and stale devices on a physical iPhone. The outbox tracks tickets and checks receipts after 15 minutes, retries failed sends with backoff, and removes DeviceNotRegistered tokens. Mocked service tests are not device-delivery proof. Only activate production after real receipt/device testing. Delivery is at-least-once; network interruptions may cause a duplicate push. Browser push is not implemented; browser users have the in-app inbox.

## 6. Support, moderation, policies and hosting

Registered verified users can submit private support/bug/feature/question feedback to the administrator inbox. **Suggest an Update** is free for every registered verified user. It accepts proposed descriptions/status/source-document links and free text including meeting corrections. It cannot publish directly. The admin reviews the patch, can amend reviewed fields, approves/rejects it, and approval commits the map revision, edit history, notifications and review status transactionally. Document input is via HTTPS source links; file attachments and discussion threads are not implemented.

Set PRIVACY_URL and TERMS_URL to your actual reviewed policies. Missing policies are labelled unavailable; no fabricated legal policy is published. Deleting a non-admin account requires recent authentication and a deliberate DELETE confirmation; its provider account, profile, follows, devices and private inbox are removed, while published edits are anonymized. An account tombstone prevents old JWTs from recreating deleted accounts. Store subscriptions must be cancelled separately. Test deletion with disposable accounts in Auth0; a failed provider request must not be represented as successful deletion.

The existing Dockerfile serves the web app and protected API. Pass the public EXPO_PUBLIC_AUTH0_* and EXPO_PUBLIC_REVENUECAT_WEB_KEY values as Docker build arguments (Expo embeds them in the browser bundle); runtime-only changes cannot configure an already-built browser SDK. Server secrets are runtime environment values, never build arguments. Use Node >=22.13, persistent private disk mounted at /data, HTTPS termination, encrypted secrets, backups, monitoring and reverse-proxy rate limits/body limits. The built-in mutation limiter is per-process/per-peer; configure a real trusted reverse proxy before public traffic. A single SQLite service is suitable for this stage; a national high-traffic deployment needs a planned PostgreSQL migration, spatial indexing, pagination/search at scale and a durable notification queue. No hosting or public domain has been provisioned here.

Manual external setup remains: Auth0 tenant/apps/API/Actions/MFA and email provider; Google Cloud OAuth; Apple Developer/App Store Connect/Sign in with Apple/APNs; Expo/EAS; RevenueCat; web billing provider; HTTPS hosting/persistent storage/domain; support operations; real privacy/terms URLs. No GitHub repository is required for manual data entry, although one is recommended for protecting source history.

Primary integration references: [Auth0 explicit linking](https://auth0.com/docs/manage-users/user-accounts/user-account-linking/link-user-accounts), [Auth0 MFA Action ordering](https://support.auth0.com/center/s/article/using-actions-mfa-authentication-method-is-missing-on-first-login), [RevenueCat web billing](https://www.revenuecat.com/docs/web/web-billing/web-sdk), [RevenueCat webhook verification/reconciliation](https://www.revenuecat.com/docs/integrations/webhooks), [Expo push tickets and receipts](https://docs.expo.dev/push-notifications/sending-notifications/).

## Current local Auth0 activation

The development tenant is connected locally with ignored `.env` and `.env.server` files. BuildWatch Web and the existing native client are authorized for `urn:buildwatch:api`. Google currently uses Auth0 development keys; replace these with your own Google OAuth credentials before production. Apple is disabled until its Auth0 connection has been configured and tested; then set `EXPO_PUBLIC_AUTH0_APPLE_ENABLED=true` and rebuild.

Complete Google consent from the BuildWatch sign-in tab and return to the application. Codex can then inspect the verified local account and run the one-time administrator bootstrap. A new login will require authenticator enrollment/MFA. No administrator has been assigned until that step succeeds. Do not distribute the local `.env.server` or runtime SQLite database.

The initial verified Google account has now been assigned the sole administrator role using the one-time server bootstrap. OTP enrollment is open in the browser; complete it and save the recovery code privately. The backend denies administrator operations until the signed token contains completed MFA proof. After enrollment, use Menu → Admin Dashboard → Edit Map to add developments or edit existing pins; use Invite Collaborators for additional editors.
